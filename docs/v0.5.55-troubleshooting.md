# 9Router fnOS 打包问题回顾 & 解决方案

> 2026-08-20 v0.5.55 重新打包过程中遇到的问题及修复

---

## 问题一：首次安装后 Internal Server Error

**现象**：fpk 安装后首次打开 9router 显示空白/500，日志报 `Cannot find module 'next/dist/compiled/cookie'`，但重启后恢复正常。

**根因**：SQLite WAL/SHM 文件属主错误。fpk 安装过程中 npm install 产生 WAL/SHM 文件（属 yangyu:Users），安装完成后9router 用户启动进程时无法打开数据库 → 所有 DB 驱动（better-sqlite3 / node:sqlite / sql.js）失败 → `getProviderConnections()` 抛异常 → catch 里连接数组为空 → 返回全部 691 个静态模型。

**关键日志信号**：
```
[DB] node:sqlite unavailable: unable to open database file
[DB] sql.js unavailable: Error: ENOENT: no such file or directory, open '.../sql-wasm.wasm'
```

**修复**：cmd/main 启动前清理 WAL/SHM 残留
```bash
rm -f "${DATA_DIR}/db/data.sqlite-shm" "${DATA_DIR}/db/data.sqlite-wal" 2>/dev/null || true
```

**教训**：SQLite WAL 模式下，`-shm`/`-wal` 文件是数据库的必要组件。跨用户/跨进程安装时，这些文件可能由构建进程（root 或其他用户）创建，导致目标用户无法打开。任何 fnOS 应用使用 SQLite 时都应在启动时检查并清理这些文件。

## 问题二：/v1/models 返回全部 691 个模型（未连接也返回）

**现象**：数据库有 21 个 provider 连接，但 `/v1/models` 返回 691 个模型（所有内置 provider 的静态列表）。

**根因**：上游 `route.js` 的 `buildModelsList()` 用 `connections.length === 0` 判断是否 DB 不可用：
```js
try {
  connections = await getProviderConnections();
} catch (e) {
  console.log("Could not fetch providers, returning all models");
}
// ...
if (connections.length === 0) {
  // 返回全部静态模型
}
```
当 DB 驱动加载失败（问题一），catch 执行后 connections 为空，走进了静态模型分支。而 `connections.length === 0` 同时覆盖了"DB 真不可用"和"DB 可用但无连接"两种情况。

**修复来源**：上游 PR #3267 引入 `dbAvailable` 标志：
```js
let dbAvailable = true;
try {
  connections = await getProviderConnections();
} catch (e) {
  dbAvailable = false;
}
// ...
if (connections.length === 0) {
  if (!dbAvailable) {
    // 仅 DB 真不可用时返回静态模型
  }
  // DB 健康但无连接 → 返回空
}
```

**教训**：DB 连接失败和"DB 正常但无数据"是两个不同语义，不能用同一个 `length === 0` 判断。任何依赖 DB 的 API 都应区分这两种情况。

## 问题三：install_callback 在 x86 离线版上误触发在线构建

**现象**：x86 离线 fpk（已含 .next-cli-build + node_modules）安装时，install_callback 仍执行 `npm install` + `npm run build`，破坏已有的 node_modules。

**根因**：install_callback 检测 `.next-cli-build` 只查 `${APP_DIR}/server`，但 fnOS 解压 fpk 时可能先放到 `${APP_DIR}/target/server`（target 是指向 @appcenter 的软链）。路径不在检测范围内 → 判定"未构建" → 执行在线构建 → npm install 与已有 node_modules 冲突（ENOTEMPTY）。

**修复**：多路径检测 + node_modules 链接兜底
```bash
for check in "${SRC_DIR}/.next-cli-build" "${SRC_DIR}/.next" \
             "${APP_DIR}/target/server/.next-cli-build" "${APP_DIR}/target/server/.next"; do
    [ -d "$check" ] && BUILT=1 && break
done
# 若 SRC_DIR 缺 node_modules 但 target 有，创建符号链接
```

**教训**：fnOS 应用有两种部署布局（`APP_DIR/server` vs `APP_DIR/target/server`），install_callback 必须两条路径都检测。对 x86 离线版，在线构建是破坏性操作——有构建产物就绝不应该再跑 npm install。

## 问题四：NAS 上 git 缺少 remote-https 模块

**现象**：NAS 上 `git clone https://...` 报 `git: 'remote-https' is not a git command`。

**根因**：fnOS 自带精简版 git（`/var/apps/git/target/bin/git`），通过 `/usr/local/bin/git` 符号链接优先于 apt 安装的完整版。精简版不含 `git-remote-https`。

**修复**：
1. `sudo apt install git`（Debian）安装完整版到 `/usr/bin/git`
2. `sudo rm /usr/local/bin/git`（删除旧符号链接）

**教训**：fnOS 精简版工具链优先级高于系统包。安装完整版后需要移除旧符号链接，否则 PATH 仍指向精简版。

## 问题五：数据库恢复后前端显示空白

**现象**：手动恢复旧数据库后，curl 测试正常（200），但浏览器打开仍显示空白/初始状态。

**根因**：恢复数据库后未重启服务，运行中的进程仍持有旧的空数据库连接。node:sqlite 的 WAL 模式下，进程启动时建立的连接不会自动刷新到新文件。

**修复**：恢复数据库后必须 `appcenter-cli stop` + `appcenter-cli start` 重启服务。

**教训**：任何数据库文件的替换/恢复操作后，必须重启服务进程。SQLite WAL 模式的进程级连接缓存不会自动感知文件变化。

## 问题六：NAS 构建环境 git 无法克隆 GitHub

**现象**：NAS 上 `git clone` 报 `Host key verification failed` 或 `remote-https` 不可用。

**根因**：
1. fnOS 精简 git 无 HTTPS 支持（问题四）
2. 无 SSH key 配置
3. gh CLI token 缺少 `admin:public_key` scope 无法自动添加

**修复路径**：
- 方案 A（推荐）：安装完整 git + gh auth token 配置 HTTPS 凭据
- 方案 B：生成 SSH key + 手动添加到 GitHub

**教训**：NAS 构建环境需要完整的 git（含 HTTPS/SSH 支持）。fnOS 精简版不满足构建需求。

## 通用教训

1. **SQLite WAL 文件是数据库的必要组件**：任何使用 SQLite 的 fnOS 应用，install/uninstall 回调都不能删除 WAL/SHM，启动时应清理残留（防跨用户问题）。
2. **fnOS 两种部署布局**：`APP_DIR/server` 和 `APP_DIR/target/server`（target 是软链），回调脚本必须两条路径都检测。
3. **离线版不应触发在线构建**：x86 离线 fpk 自带 node_modules + 构建产物，install_callback 有构建产物就 skip，不要用 npm install 破坏已有依赖。
4. **数据库操作后必须重启服务**：SQLite 进程级连接缓存，文件替换后需重启才能生效。
5. **fnOS 工具链优先级**：精简版 > 系统包，需手动调整 PATH 或移除旧符号链接。
